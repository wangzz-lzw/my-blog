# Proposal

## Why

图片上传现在是**一次性动作**：选文件 → sha256 算出 `img/<hash>.<ext>` → 传 OSS → 拿到 `/img/...` 地址 → 用完即忘。服务端不记录任何东西，所以：

- **同一张图想再用一次，只能重新上传**。封面要复用一个系列的主视觉、或者把同一张图放进两篇文章，都得再从硬盘里找一遍。好在内容寻址会命中已有对象（`deduped: true`），所以成本是多点几次，不是多存一份——但"知道那张图存在"这件事，系统里没有任何地方体现。
- **传错了只能瞎猜**。上传完才发现在列表页里缩略图太小、或者封面裁剪后不好看，没有地方能回头看一眼全部图片。
- **82 个已有对象是黑盒**。`img/` 前缀下已经堆了正文配图、封面、头像，没有清单，也不知道哪张在用、哪张是早期试验留下的。

也就是说：这套系统有"写入图片"的能力，没有"图片"这个实体的概念。图床要补的就是这一层。

## What Changes

- **新增 `Image` 表**：每次成功上传记一行（key、sha256、扩展名、MIME、字节数、宽高、用途、上传人、创建时间）。内容寻址意味着 key 唯一，所以重复上传命中已有对象时不新增行，只更新 `usage` 与 `lastUsedAt`。
- **首次回填**：一次性脚本扫 OSS 的 `img/` 前缀，把已有对象补进表。回填不存在的对象不报错、只跳过（脚本可反复运行）。
- **新增 `/admin/images` 图床页**（仅管理员）：网格展示缩略图 + 文件名 + 大小 + 尺寸 + 用途 + 上传时间，支持按用途筛选与按 key/哈希搜索，分页。点击任意一张可复制站内地址。
- **只读，不提供删除**。图片是跨实体共用的（同一张可能是某篇文章的封面、另一篇的正文配图、某个读者的头像），删错不可恢复；而"引用检查"需要扫描全部正文与关联字段，成本与风险都不划算。真的需要清理时走数据库或 OSS 控制台。
- **封面选择器**：文章编辑器的封面行在「上传」旁多一个「从图床选」，打开一个选择面板（复用图床的网格），选中后回填 `cover`。目前只接封面这一个入口。
- **预留**：`Image.usage` 记最近一次用途（`avatar | cover | image`），列表按用途筛选；但**不做**"按用途硬隔离"——同一次上传可能先当封面、后又被正文引用。
- **保持现有上传行为不变**：`/api/upload` 的请求/响应、内容寻址去重、`/img/<key>` 代理、`READER` 也能传头像——这些一条都不动，只是在成功路径上多写一行记录。

## Capabilities

### New Capabilities

- `image-library`: 图片作为一等实体的契约 —— 上传时记录哪些信息、内容寻址下重复上传如何合并、历史对象如何回填、图床页展示什么与不能做什么、选择面板如何回填、以及非管理员与 OSS 未配置时的降级。

### Modified Capabilities

（无。`admin-editor` 的八条要求都不变——本变更只在封面行旁加一个额外入口，视图切换、全屏、内容保持等契约不受影响；`markdown-render` 完全不动，正文插入路径保持原样。）

## Impact

- **代码**：新增 `prisma/schema.prisma` 的 `Image` 模型 + 一条迁移；新增 `lib/images.ts`（记录、查询、回填）；改 `app/api/upload/route.ts`（成功路径多写一行）；新增 `app/(site)/admin/images/page.tsx` 与 `components/admin/ImageLibrary.tsx`（网格 + 筛选 + 搜索）、`components/admin/ImagePicker.tsx`（封面选择面板）；改 `components/admin/PostEditor.tsx`（封面行的「从图床选」）；改 `app/(site)/admin/layout.tsx`（导航加「图床」）；新增 `scripts/backfill-images.ts`。
- **数据**：一张新表 + 一条迁移，不改动 `Post` / `User` / `Tag` / `Comment`。回填脚本只读 OSS、只写 `Image` 表，不动任何既有数据。
- **依赖**：无新增。图片尺寸解析用**已经存在的** `sharp` 之外的方案——`ali-oss` 返回的对象头不含像素尺寸，因此宽高在**上传时**由服务端解析（`image-size` 一类纯解析库，或对 JPEG/PNG 手写头部读取），拿不到时留空而不是拒绝上传。回填阶段若无法取得尺寸，同样留空。这一条需要在设计阶段定下具体做法，避免为了一个可选字段引入重依赖。
- **风险**：上传是高频路径，多写一行不能拖慢或让它失败——写库异常必须被吞掉（图片已经存进 OSS 了，记录失败不该让用户重传）；回填脚本对大 bucket 要分页；`READER` 上传头像也会进表，所以图床里会出现普通用户的头像，需要确认这不违背"仅管理员可见"（图床页本身只给管理员，但列表里会显示上传人）。
- **验证口径**：真实 HTTP 上传一张新图 → 表里出现一行且字段正确；同一张图再传一次 → 行数不变、`lastUsedAt` 更新、`deduped: true` 仍然返回；回填脚本连跑两次结果幂等；图床页在管理员下正常、非管理员被重定向；封面选择面板选中后 `cover` 被正确回填并能保存；`tsc` 与 `build` 通过。
- **不在本次范围**：删除/回收站、批量操作、图片重命名或打标签、按文章归类、正文插入的图片选择（这次只接封面）、CDN 或图片处理（裁剪/压缩/WebP 转换）、把历史 OSS 直链批量改写成站内地址、非管理员访问图床的只读视图。
