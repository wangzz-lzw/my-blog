# 全栈交付

一套从需求走到上线、并要求每条结论都能被独立验证的工作方式。

**核心主张**：能测的不靠看，能查的不靠猜，能留档的不靠记。
这个项目里每一次"看起来对"都最终被证伪过——日期列被压成 0 宽、整页多滚 31px、
后台被裁 98px、锚点落点被页头压住 60px。这些没有一个是肉眼在截图里能发现的。

---

## 0. 三条铁律

1. **先定义"对"，再动手。** 动手前写不出可观测的验收条件，就是还没想清楚。
2. **每条断言都要能真实执行。** 拿不到确定值的验证等于没验证。
3. **失败先分账。** 断言失败时先问"是代码错，还是我的期望值错"，不要直接改代码去迎合测试。

第 3 条不是洁癖。本项目两处"失败"最后查明是**测试期望写错**——把 `19000px` 换算成了末块、
把偶数次循环当成了最后一次驱动。如果当时去改实现来迎合错误期望，会引入真实缺陷。

---

## 1. 需求 → 规格

### 先问，再写

**只问会改变可观测行为的**，不问实现偏好。判断标准：这个答案会不会让两个方案产出不同的用户可见结果？

有效的三问（本项目实例）：

- 大纲显示哪些层级 → 决定 DOM 内容与跳过规则
- 除了跳转要不要滚动高亮 → 决定是否引入 spy 循环
- 窄屏怎么处理 → 决定是删元素还是加折叠交互

无效的问法：「用 Radix 还是原生？」——这是实现细节，工程师自己定并在设计里说明理由。

### 规格写行为，不写实现

```
❌ 用 OverlayScrollbars 初始化 textarea 的滚动
✅ 分屏时两侧滚动条 SHALL 使用同一套自绘外观；编辑区 MUST NOT 显示浏览器原生滚动条
```

判断法：如果换一套实现但用户看到的完全一样，这条就不该进规格。

### 每条需求至少一个场景

`WHEN`（触发）+ `THEN`（可观测结果）。场景是最小测试单元的候选，
本项目 146 条需求配了 317 个场景，比例约 1:2——低于这个比例通常意味着边界没想。

## 2. 设计：把"不选它"也写下来

### 先读现状，再决策

动手前必须确认三件事，且都要在文档 Context 里给出出处：

1. **这东西现在是什么**（不是"应该是什么"）
2. **哪些前提已经被证实**（实测数据，不是经验判断）
3. **既有的同类实现长什么样**（复用惯例优于发明新写法）

本项目的实例：实现分屏联动前，先实测确认了 `position.start.line` 能从 mdast 带到 hast、
`textarea.scrollTop` 可写且 `scrollbar-width: none` 后仍可滚，才敢把方案写进设计。
没有这两条实测，整个方案的地基是猜的。

### 每个决策必须写"备选（否）"

只写"我选 A 因为 A 好"是没做的设计。要写**为什么不是 B**：

```
D2 布局：借用左侧留白，不把壳改成两列
- 为什么：只加宽壳会让正文整体右移约 68px，右侧还多出一块空白
- 备选（否）：.article-shell 改 grid-template-columns: 180px minmax(0,1fr)
```

这条纪律的价值：三个月后有人想改布局时，能看到这个坑已经踩过了。

### 风险表：每条风险必须配对策

```
[sticky 失效] 祖先有 overflow:hidden 会退化成普通块 → 沿 .app-scroll-content → main → .article-shell 逐层核对
```

有风险没对策 = 没想清楚，不是"已知风险"。

## 3. 任务拆分

- **每个任务自带验证方式**，不是最后统一"测试一下"。写成「做完怎么确认它对」。
- **按依赖排序，不按文件排序。** 先「行号注入」再「联动算法」再「接线」，因为后者的输入是前者的产出。
- **每组自己带测试**，不堆到最后。晚出现的测试会一次性暴露前面所有组的问题，然后你分不清是谁引入的。
- 拆分粒度：一个任务一个会话内能完成，且能独立验证。

## 4. 实现：把降级当主路径设计

### 复用既有惯例

动手前搜一遍"同类问题之前怎么解的"。本项目里同一个模式被复用了三次：

```
ListScrollPane  →  PostOutline  →  useEditorScrollSync
（位置预缓存 + 滚动帧只写 DOM + rAF 合并 + ResizeObserver 重测）
```

复用不只是省事——它让后来者只需要理解一套心智模型。

### 降级路径先写，不是事后补

每个交互至少要考虑四层：

| 层 | 问什么 |
|---|---|
| 无 JS | SSR 出来的 HTML 能用吗？会不会出现空栏/死控件？ |
| 减少动效 | `prefers-reduced-motion` 下还看得懂吗？ |
| 触屏 | `hover: none` 下悬停类交互还有意义吗？ |
| 窄屏/打印 | 被挤死吗？打印只有一屏吗？ |

⚠️ **门控标记要确认作用域**。本项目踩过：`html.js-ready` 只在首页才加
（`layout.tsx` 里有 `location.pathname === '/'`），拿它给编辑器门控会得到
「编辑器始终显示原生条」或「无 JS 时完全没有滚动条」——两种都是静默失败。
自己打一个局部标记（`data-synced`）比复用全局标记安全。

### 注释写"为什么"，尤其写"否则会怎样"

```
✅ 轨道只覆盖正文区，不能压到下方的字符数状态条上
✅ 用 opacity 而不是 display:none 来隐藏：display:none 会让 clientHeight 变成 0，
   而测高正是判断"要不要显示"的依据，两者会互相锁死
❌ 设置轨道高度
```

「否则会怎样」是注释里信息密度最高的部分，它记录的是**已经发生过的事故**。

## 5. 验证：分层，且断言语义

### 三层递进，不许跳层

| 层 | 手段 | 抓什么 |
|---|---|---|
| 1 | `tsc --noEmit` + 生产构建 | 类型、边界、RSC/构建问题 |
| 2 | 真实 HTTP（Node `fetch` + cookie jar） | 状态码、响应体、鉴权、缓存头 |
| 3 | 真实浏览器（CDP / 无头 Chrome） | 布局、滚动、计算样式、交互 |

第 2 层**不要用 `curl -d` 拼 JSON**——在 Windows/pwsh 环境下引号与编码会静默出错，
用 Node `fetch` + 手搓 cookie jar 可靠得多。

第 3 层用 CDP 而不是截图：截图只能证明"看起来对"，
`getBoundingClientRect()` 能证明"标题顶部是 85px，页头是 61px，所以没被压住"。

### 断言语义，不断言观感

```
❌ 断言"预览区滚动了一点"           → previewScrollTop > 0
✅ 断言"预览落在对应的块上"         → 首可见块的 data-src === 编辑区顶部行算出的期望块
```

后者需要你在实现里先埋好可断言的坐标（本项目是 `data-src`）。
**为了可验证而设计数据结构，是值得的成本。**

### 断言必须写死可执行阈值

```
❌ "落点差不多对"
✅ headTop >= headerH && Math.abs(headTop - (headerH + 24)) <= 40
```

### 降级必测

无 JS 这条尤其容易假通过：`Emulation.setScriptExecutionDisabled` 对已 hydrate 的页面无效。
可靠办法是**检查 SSR 出来的 HTML 本身**——本项目用五个不变量确认降级正确：

1. SSR 未预置 `data-synced`（原生条保留）
2. 自绘轨道无 `data-visible` 时 `opacity: 0`
3. 隐藏用 `opacity` 而非 `display`（避免测高死锁）
4. `scrollbar-width: none` 仅作用在 `[data-synced]`
5. SSR 的 textarea 无内联隐藏样式

## 6. 收口

- **文档同步**：改了什么行为，就改哪一节；并写清"为什么"（本项目的 `docs/DEVELOPMENT.md` 有专门的排障速查表）。
- **技术债显式登记**：发现但不能当场修的，写成清单而不是忘掉。本项目登记了 11 条，包括「死代码」「两条改邮箱路径口径不一」「`viewportOf()` 两份实现」。
- **不做范围外的事**：实现过程中发现别的 bug，报告并询问，不要顺手改——那会让变更无法回滚。

## 7. 踩坑目录（本项目实测，可直接当检查表）

| 现象 | 根因 | 修法 |
|---|---|---|
| 移动端日期列被压成 0 宽、压住标题 | `.entry.has-cover` 特异性 0,2,0 高于 `.entry` 0,1,0，720px 断点只改后者被 900px 规则盖掉 | 窄屏**重写 `grid-template-areas`**，不要只改列宽 |
| 整页多滚 31px | `.sb-content` 的 `min-height:100%` 与列表容器高度叠加 | `body:has(.x) .app-scroll-content { height:100%; min-height:0 }` |
| 后台页面底部被裁 33–98px | 滚动库缓存了「无溢出」，内容异步长高后没重算 | `ResizeObserver` → `instance.update(true)`，60ms 防抖 |
| 自定义滚动条出现 ▲▼ 箭头 | Chrome 一旦接管 `::-webkit-scrollbar` 就退回经典渲染 | 放弃该方案，换 JS 库接管 |
| 自己给的 viewport 完全不滚 | 自建 viewport 变成 `height:auto` | 用库默认 elements + 自己的内容包裹层 |
| `permanentRedirect` 500 | 中文 slug 直接进 `Location` 头 | `encodeURIComponent` |
| 冲突提示文案时对时错 | `Promise.all` 并发查询顺序不定 | 改**顺序**查询，先报"更直白"的那个 |
| 中文文件变乱码 | PowerShell `Set-Content` 写成非 UTF-8 | 用编辑工具，或 `Out-File -Encoding utf8` |
| 自定义组件丢属性 | 组件映射（如 `pre → CodeBlock`）没透传 props | 显式透传，否则下游 `data-*` 全丢 |
| 需要测量的元素被 `display:none` | 隐藏时 `clientHeight=0`，测不到就不显示，永久死锁 | 用 `opacity` 隐藏 |
| 元素定位恒为 0 | CSS `translate` 属性与 inline `transform` 相互覆盖 | 位置走 CSS 变量 |
| 受控 textarea 改变高度后不重算 | 改 `value` 不触发 `resize`/`input` | 父级传 `version` 显式通知重算 |
| 锚点落点被粘性页头压住 | 跳转只减了 8px，没减页头高度；全站无 `scroll-margin-top` | 按 `getBoundingClientRect().height` 动态算偏移 |
| 跳转后落点越滚越偏 | 路径上懒加载图片陆续落位把目标顶下去 | 停稳后重算差量校正一次（`behavior:"auto"`） |
| `focus()` 抢走滚动位置 | 目标尚不可见时部分浏览器无视 `preventScroll` | 先校正位置，**最后**再 `focus` |
| 回声振荡（两侧互推） | 程序化写入触发对方 `scroll`，对方又反向驱动 | 写入时记录 `{side, target}`，受控侧比对已达目标值就丢弃；短窗口只兜底"目标等于当前位置、不触发事件" |

## 8. 反模式

| 反模式 | 为什么不行 | 换成 |
|---|---|---|
| 截图当验证 | 只能证明"看起来对" | 量 rect / computed style / 属性 |
| 用 `setTimeout` 猜窗口做去抖 | 弱机/慢滚会漏，且不可解释 | 用确定性事实（父级传值、目标值比对） |
| `display:none` 门控需要测量的元素 | 测高死锁 | `opacity` + `pointer-events` |
| 复用"只在某页生效"的全局标记 | 静默失败，最难查 | 组件自己打局部标记 |
| 失败就去改实现迎合测试 | 可能引入真缺陷 | 先分账：代码错 / 期望错 / 时序错 |
| 静默吸收超出规格的改动 | 变更无法回滚，也无法 review | 报告 + 询问 + 单独变更 |
| 只写"我选 A 因为 A 好" | 三个月后没人知道为什么不是 B | 写「备选（否）」 |
| 风险没有对策 | 那不是"已知风险"，是没想清楚 | 每条风险配缓解措施 |
| 报"全部通过"而不提断言改过 | 读者无法判断可信度 | 明确说明哪次是断言写错 |

## 9. 完成定义

一项工作算完成，需要同时满足：

- [ ] 每条规格需求都有对应场景，且场景被真实执行过（不是"应该会"）
- [ ] `tsc --noEmit` 与生产构建通过
- [ ] 关键路径有真实浏览器测量（rect / computed style / 语义属性断言），有量化阈值
- [ ] 降级四层都验过：无 JS / 减少动效 / 触屏 / 窄屏（+ 打印若相关）
- [ ] 设计文档记录了决策与「备选（否）」；风险都有对策
- [ ] 文档同步；技术债显式登记而非遗忘
- [ ] 报告里如实区分「代码修了什么」与「断言改了什么」
